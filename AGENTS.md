# AI Career Copilot — Codex instructions

Use these instructions for work in this repository. First inspect the current source and git status; preserve existing user changes and follow any more-specific instruction file that applies to the files being changed.

## Project and sources of truth

AI Career Copilot is a locally runnable job-search workflow with a React frontend and a Python/FastAPI backend. The current product overview and development setup are in [README.md](README.md); backend-specific notes are in [backend/README.md](backend/README.md). [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) records current system boundaries and invariants.

Treat implementation and tests as the authority for current behavior. PROJECT_SPECIFICATION.md is explicitly the original proposal, and dated reports or design/audit documents are historical snapshots. Do not infer current behavior from them without checking the code. Do not assume main, a previous branch, or a prior task summary represents the active worktree.

## Repository map

- backend/app/: FastAPI API, SQLAlchemy models, services, integrations, and persisted agent runtime.
- backend/alembic/: database migrations; backend/tests/: backend and API tests.
- frontend/src/: Vite, React, and TypeScript application; frontend/tests/: Node test-runner tests.
- docs/: architecture/runtime guidance and historical design, audit, investigation, and milestone reports.
- .github/workflows/ci.yml: CI checks. Dockerfile: production image build.

Codex instruction files use standard AGENTS.md discovery behavior. Check applicable instructions before editing nested areas; add a nested instruction file only when a lasting subsystem-specific rule warrants one.

## Commands and verification

Run backend commands from backend/:

~~~powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
.\.venv\Scripts\python.exe -m pytest -ra
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic check
~~~

Run frontend commands from frontend/:

~~~powershell
npm ci
npm test
npm run build
npm run dev
~~~

npm test uses Node's built-in test runner. CI currently runs the backend suite, frontend production build, and a Docker image build; consult .github/workflows/ci.yml for its exact environment.

Backend tests require PostgreSQL-specific behavior. Fixtures may create a test database and drop/recreate tables; migration tests also use a scratch database. Before running them, verify that the effective TEST_DATABASE_URL or configured test target is disposable. Never point destructive test fixtures at production or valuable development data. Tests use fake clients or mocked transports for external providers; do not add live provider calls to tests.

For model or schema changes, inspect backend/app/models/, export each new model from backend/app/models/__init__.py, create and review the Alembic revision, and run relevant migration tests and alembic check against a safe database. Do not accept autogenerated migration output without reviewing it.

Choose verification based on the changed area. Run npm test and npm run build for frontend changes, and relevant pytest coverage for backend changes. Documentation-only edits normally need link/content checks and git diff --check, not the full application suite. Report which checks actually ran and their results.

## Architectural invariants

- PostgreSQL and migrations: PostgreSQL is the supported database. Keep SQLAlchemy models and Alembic migrations aligned. Alembic discovers metadata through app.models; an unexported model can make autogenerate propose destructive changes.
- Ownership and request security: there is no user login; private candidate resources are scoped to the server-selected local profile. Preserve the desktop bearer-capability check, the loopback Host and Origin checks, and ownership checks in routes and services. Do not rely on a caller-supplied ID as proof of ownership.
- Transactions: the agent runtime and application services flush but do not own commits; their caller owns the transaction. Routes commit their own writes. The synchronous agent API runner commits run creation, claim, and execution in separate phases. Preserve this ownership and the tested separation of provider calls from persistence writes.
- Agent runs: run status transitions and retry rules belong to the runtime. Idempotency keys are shared across agents and must be namespaced. Preserve PostgreSQL advisory-lock and partial-unique-index protections; do not add a competing deduplication mechanism without deliberately changing the design.
- Evidence and prompts: analysis, matching, and cover-letter outputs are data, not control instructions. Keep generated claims grounded in persisted job/profile/resume evidence. Bump the relevant prompt version whenever prompt behavior changes so prior results remain attributable to their inputs.
- Resume history and privacy: master resume uploads append immutable document versions linked to the previous version. Text extraction is local; resume-based Gemini features may send selected evidence to the configured provider and are guarded by CAREER_COPILOT_ENABLE_RESUME_AI (production defaults it off unless enabled). Do not change this data flow or feature gate silently.
- Discovery and availability: discovery admits only reviewed direct-job sources and validates crawled page evidence. A failed or inconclusive re-verification must not mark a job closed or replace accepted vacancy content. Preserve durable per-user and global provider-operation limits.


## Configuration and subsystem entry points

- Backend settings are defined in backend/app/core/config.py and loaded with the CAREER_COPILOT_ prefix. The backend .env is resolved from the backend working directory. Use backend/.env.example for names and safe defaults; keep real credentials in ignored local configuration or process environment.
- Frontend build settings use VITE_ variables from frontend/.env. A blank VITE_API_BASE_URL uses same-origin paths and the Vite development proxy. Never put provider credentials in frontend settings.
- Production settings have additional safety checks and defaults. In particular, do not assume development cookie, CORS, provider, database, or resume-AI settings are appropriate for production; check config.py and its tests when changing configuration.
- For database, agent, transaction, evidence, or document-lifecycle changes, consult docs/ARCHITECTURE.md and the affected source/tests. For local API access and profile work, inspect backend/app/api/capability.py, backend/app/api/origin.py, backend/app/api/deps.py, backend/app/services/candidates.py, and tests/api. For discovery sources or verification, inspect the source registry, classifier, service, and focused tests.
- The desktop runtime described in docs/DESKTOP_RUNTIME.md is an experimental foundation, not a packaged application. Keep it separate from ordinary browser development and do not describe it as ready for end users.
